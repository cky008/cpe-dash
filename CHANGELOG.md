# Changelog

All notable changes to 烽燧 FengSui (`cpe-dash`). Versions follow [Semantic Versioning](https://semver.org/). Each release section opens with `### Highlights` (a few changes worth a short paragraph); the GitHub release lists the other changes by their lead sentence and links here for the details.

## [Unreleased]

### Added
- **SMS on routers of other brands.** The SMS page, verification codes, Recently deleted, contacts, Telegram, webhooks and the agents' SMS tools now work on ZTE routers (both interfaces, goform and zWRT: read, send, mark as read, delete), OpenWrt routers with a Quectel or Fibocom module (read and delete; send where QModem is installed), Tozed / ZLT routers such as the China Unicom VN007 (read and send) and FiberHome routers (read, mark as read, send plain English text, delete a whole conversation). Each is implemented from the brand's interface notes and has not been checked on a real router; "SMS" in the guide says what differs per brand. Pinsu and NRadio have no SMS: no record of an SMS interface was found for either.
- **ZTE routers whose firmware spells the interface `reqproc`** (the ZXIC firmware of many rebadged 4G routers and MiFis) connect now: FengSui signs in with their own login (the user name, and the SHA-256 of a nonce and the password) and signs each write with the `CSRFToken` they hand out. Choose "ZTE (goform web interface)" or leave the brand on automatic. On a router with the goform pages nothing changes.
- **SMS writes on those routers are experimental writes**: on by default, sent once, read back afterwards, with a `WRITE_READBACK_MISMATCH` alert when the router did not do what was asked. Turn off "Send and manage SMS" under Settings → Device to stop them. A send goes to one recipient at a time, and once one went out a refusal fails the recipients not reached yet instead of sending anything again.
- **FengSui keeps the read state where the router cannot.** A Tozed router has no command to mark a message read, and a modem on OpenWrt marks every message read as soon as it is listed. On those two, what you have not read is what FengSui remembers, marking as read writes nothing to the router, and on OpenWrt the messages you send are kept by FengSui only (the modem stores none).
- **The console and Telegram offer only what the router can do with SMS.** A router that cannot send (an OpenWrt router without QModem) shows no New message button, reply box or Telegram reply; one that cannot delete (a Tozed router) shows no delete button; and on a FiberHome router, which deletes a whole conversation at a time, the delete is one "Delete conversation" button at the top of the conversation. The daemon learns this from each listing and gives it in `SmsStatus.abilities` (`null` until the first listing, when everything is offered as before).
- **FiberHome's Pro series (such as the LG6851F).** FengSui recognises the Pro series on its own path (`/fh_api/`) and reads its signal (one serving cell), this month's traffic and SMS, and marks messages read there. Its answers are encrypted with a key worked out from the session id and a token. FengSui takes the token the router hands out, unsealed with the RSA key fixed in the series' firmware (the same key is in every such router's web page), and falls back to the token on record; it settles the key on a login-free call before any password goes out, so a firmware neither token opens gets no password at all. Nearby cells, locks, reboot, and sending or deleting SMS are not in its interface notes, so FengSui does not offer them there: Settings → Device shows no switch for them, the write gate refuses them before any session, and the SMS page hides the buttons it cannot use. The driver says which form of FiberHome's interface a router speaks when it identifies it, and the gate, Settings → Device and the Supported devices table all go by that.
- **The AI agent test covers cell locks and 5G band locks, and asks what the router's own page offers.** Its prompt now has the agent lock the cell in use (each of a 4G and a 5G one) and, where 5G is in use, the 5G band in use, each put back right after, and copy word for word any reason FengSui gives for refusing a write (a router that locks 5G cells only, a 5G band lock the module cannot take). Once the writes are done it asks you to look at the router's own web page for its network modes and its cell and band locks, so a report says what a router has that FengSui does not do yet; the device report issue form has a field for it. A ZTE router on the `/reqproc/` spelling of the interface says so in its device report (`identity.variant`).
- **The AI agent test does only the SMS steps the router can.** The test sends its own message first, so it offers SMS only where the router can send; its confirmation says what follows on this router (whether marking read reaches the router, and whether the two test messages are deleted, as a conversation, or left), and the prompt tells the agent to go by `abilities` in `get_sms_status`, which now also says where marking read lands (`markRead`: `router` or `fengsui`).
- **Redial and mobile data on ZTE and NRadio routers.** The Redial button, the mobile data switch and self-healing's automatic redial now work on ZTE routers (goform: `DISCONNECT_NETWORK` / `CONNECT_NETWORK`; zWRT: the data call's own switch, with its roaming setting kept) NRadio routers (the module bridge's data switch) and OpenWrt routers with QModem (QModem's own dial, hang-up and redial calls; its report of the connection is then the WAN state). Where a router has no redial command of its own, a redial is a disconnect followed by a connect, and the connect is always sent at the end, even when the disconnect failed. Self-healing redials only when the WAN reads as down, and leaves a router whose data you switched off alone.
- **Connected devices on ZTE goform, NRadio and OpenWrt routers.** The devices card lists what the router's own page lists: ZTE's wired and Wi-Fi station lists, NRadio's client list (wired, or the Wi-Fi band), and on OpenWrt the DHCP leases LuCI shows. A lease does not say how a device is connected, so it shows as "Link not reported" (`UNKNOWN` in `countsByMedium`) instead of a guessed badge.
- **The antenna switch on NRadio routers** (automatic, internal, external), with the codes NRadio's notes give, which number internal and external the other way round from the H168-383.
- **Traffic and carriers on OpenWrt modules.** A Quectel module's data counters (`AT+QGDCNT?` on 4G, `AT+QGDNRCNT?` on 5G, read for the mode the module is in) give its traffic and rates; a rate is never taken across the two counters. A Fibocom module lists its activated secondary carriers (`AT+GTCAINFO?`).
- **Fields the notes name are filled in.** The operator of a Tozed or FiberHome router (named from the PLMN, which is all these routers report), the PLMN where an NRadio or Pinsu router writes it in place of the operator's name, FiberHome's traffic for today, and the hardware version of NRadio's cellular module.
- **The router's own status: battery, SIM card, airplane mode and more.** Where a router reports them, the dashboard shows a mobile router's battery (charge, charging, the router's estimate of time to full or empty, its temperature), the SIM card's state, slot (the card tray or the built-in eSIM), whether it asks for its PIN and the PIN / PUK tries left, roaming and data while roaming, airplane mode, the router's own CPU and memory, each temperature sensor apart, the Wi-Fi switch and guest network, and a firmware update the router offers. They come in the same 5-second session as the signal (`telemetry.status`, `thermal.sensors`); what a router does not report is left out, never shown as 0. ZTE goform and zWRT routers report the most (battery, SIM card, roaming, data plan); FiberHome reports airplane mode; NRadio and OpenWrt report the router's uptime and load; an OpenWrt module reports its SIM card and radio switch (`AT+CPIN?`, `AT+CFUN?`), and a Quectel one its PIN tries (`AT+QPINC?`). On a Huawei router the battery and the SIM card's ICCID are read from answers FengSui already fetches: an H168-383 is sent the same requests as before.
- **More signal detail where the notes name it**: the ICCID (masked like the IMEI until revealed, and in the API's redacted copy), a 3G serving cell (RSCP, Ec/Io, scrambling code) on Huawei, ZTE goform and Pinsu routers, the uplink's MIMO layers, the RRC state and QCI on FiberHome routers, FiberHome's uplink transmit powers, bandwidth and transmission mode, ZTE's second-codeword CQI, 5G uplink bandwidth and transmit power, and a Quectel module's MCS, rank and CQI (`AT+QNWCFG="lte_csi"` / `"nr5g_csi"`), uplink bandwidth and transmit power.
- **Two new alerts: a low battery and a locked SIM card.** `BATTERY_LOW` fires when a mobile router that is not charging stays at or below `ALERT_BATTERY_LOW_PERCENT` (default 20; `0` turns it off) for a minute, and re-arms once it charges or is 5 points above; `SIM_LOCKED` fires once the SIM card has waited for its PIN or PUK for a minute. A router without a battery never raises the first.
- **`/metrics` exports the router's status**: the hottest temperature of each kind of sensor (`fengsui_router_temperature_celsius{sensor}`), the battery's charge, charging state and temperature, a locked SIM card, airplane mode, roaming, and the router's CPU and memory use. No identifier is exported.
- **Supported devices has Battery, SIM card and Airplane mode columns**, marked from each brand's facts like the other columns; an indoor CPE has no battery (`—`). These readings count as verified only from a report of their own, also on the H168-383, and a model counts as fully verified without them.
- **A third world in the live demo: a ZTE mobile router** (`?router=zte`, a 5G MU5001 on the goform interface) with a battery that runs down and charges, a SIM card in its tray, its connected devices, neighbour cells and mailbox, and the writes FengSui implements for ZTE.
- **Cellular settings: network mode, operator, SIM slot and PIN, airplane mode, roaming, APN, data limit, USSD.** FengSui can now change how a router connects to the operator, on the routers whose interface notes record the request: the network mode (ZTE, Pinsu, Tozed, FiberHome, NRadio, OpenWrt, and other Huawei HiLink models), a search for networks and manual operator selection (ZTE on both interfaces, OpenWrt, other Huawei models), the SIM slot (ZTE), entering the SIM PIN and switching "ask for the PIN at start" (ZTE, and Quectel modules on OpenWrt), airplane mode (FiberHome, OpenWrt), data roaming (ZTE, other Huawei models), the access point (ZTE, OpenWrt), the router's own monthly data limit (ZTE), clearing the router's traffic counters (other Huawei models) and USSD (ZTE goform, other Huawei models). Each is an experimental write like the others: on by default, sent once, read back, and switched off per feature under Settings → Device. The verified H168-383 gets none of them yet: its requests are unchanged.
- **A change that takes the internet down is put back after 3 minutes.** A new network mode, an operator picked by hand, another SIM slot or another access point can leave the router without service. FengSui reads the earlier value in the same session that writes the new one, and if the WAN stays down for 3 minutes it writes the earlier value back, whoever made the change (console, token, agent). It leaves things alone when the WAN is up, mobile data is off or airplane mode is on, and keeps counting across a daemon restart. Three alerts report it: `SETTING_ROLLED_BACK`, `SETTING_ROLLBACK_FAILED`, and `SETTING_NOT_ROLLED_BACK` where the earlier value could not be read. Turning mobile data off or airplane mode on is never undone: you asked for it.
- **A SIM PIN is sent once, and only with attempts to spare.** FengSui enters a PIN or switches the PIN lock only while the router reports more than one attempt left, shows that count in the confirmation, and never tries again after a refusal. With no count, or one attempt left, it sends nothing and points you to the router's own page. It does not enter a PUK or change the PIN, and the PIN is kept nowhere.
- **USSD codes, with the operator's answer shown and not kept.** Send a code such as `*100#`, read the answer, reply to a menu or end the session. The code and the answer appear in no log, audit entry, write record or event; MCP marks the answer as untrusted text.
- **A "Cellular settings" section in the controls drawer.** It shows the settings the connected router has, each with a confirmation that says what the write risks: the 3-minute fallback, that airplane mode stays on until you turn it off in FengSui, or how many PIN attempts are left. The section loads on demand and reads the settings when you open it.
- **REST routes and MCP tools for all of it.** `GET /api/cellular` and `POST /api/cellular/refresh` read the settings; eleven routes under `/api/control/` (`network-mode`, `operator-scan`, `operator`, `sim-slot`, `sim-pin`, `airplane-mode`, `roaming`, `apn`, `data-limit`, `traffic-reset`, `ussd`) write them with `confirm: true`. MCP gets `get_cellular_settings` and one write tool per setting, each needing `confirm: true`, `MCP_ALLOW_MUTATIONS` and the token's permission, and listed only where the router has the setting. Telegram has no new commands.
- **On ZTE routers the access point goes into a profile of FengSui's own.** The router's profiles are never edited: FengSui adds one profile named `FengSui`, overwrites only that one afterwards, and going back makes the earlier profile the default again. On goform routers the operator and the access point are changed the way the router's page does it: the connection is taken down first and connected again at the end.
- **More antenna and lock choices on NRadio routers**: both antennas at once, and a lock on a channel without a PCI.
- **Supported devices has columns for the new settings**: the SIM card column also covers the slot switch and the PIN, the airplane mode column its switch, and there are new columns for network mode and operator, data settings (roaming, APN, data limit, counters) and USSD.
- **The live demo shows the cellular settings** on the ZTE mobile router (`?router=zte`: a network search, the operator, the SIM slot and PIN, roaming, the access point, the data limit and USSD) and on the unverified Huawei model (`?router=other`: network mode, operator, roaming).
- **A send to a FiberHome router is checked first.** Its firmware hands a message's text to a command line, so FengSui sends printable ASCII only and never text with a backquote, a dollar sign, a double quote or a backslash; nothing goes out otherwise.

### Changed
- **Uptime shows "—" on a router that reports none of its own.** On routers of other brands the uptime came from the connection's duration; now a router that reports no uptime of its own lists `uptime` under `unavailable`, and the console shows "—" there. NRadio and OpenWrt routers report theirs.
- **The controls drawer's notes on the 5G-only mode and DDoS protection speak plainly**: they say what FengSui does not offer and why, instead of calling it missing from the "backend contract".
- **Every write goes through the router interface** (`RouterBackend`): redial, self-healing's redial, mobile data, the security switches, Wi-Fi 7, the antenna and the access-control writes are verbs each brand answers, as SMS and the locks already were. On an H168-383 the requests are the same as before, byte for byte.
- **ZTE goform cell locks follow the community's ZTE script.** An NR cell lock names its subcarrier spacing in kHz (any of 15, 30, 60, 120, 240) where the driver wrote a 0 / 1 code, and a cell lock is cleared with zeros (`0` / `0,0,0,0`) where it wrote ones. A 4G goform router whose network mode reads `NETWORK_auto` is written that name, and a 5G mode is refused there.
- **A ZTE router's login result 2 no longer latches the breaker by itself.** ZTE's own page calls it another user signed in: while the router reports attempts left and no lock, FengSui yields as for anyone else signed in, and only a lock (or no count to go by) latches the breaker.
- **SMS goes through the same router interface as everything else** (`RouterBackend`): listing, the login-free unread count, sending, marking read and deleting are verbs each brand answers. On an H168-383 the requests are the same as before, byte for byte.
- `SmsStatus.via` and `SmsSyncSummary.via` can be `driver` (another brand's own listing); `SmsCounters.localMax` is `0` where the router does not report its capacity (the console then shows the count alone, and no storage alert is raised), and `SmsCounters.newest` is set on a router whose counts alone would miss a new message. `SmsSyncSummary.mode` is the sync that was done: a brand that lists everything at once reports `full`.
- **Supported devices shows SMS per model**, with two marks in the cell where reading and sending differ (reading `?`, sending `△` with its condition under the brand's table).
- **The writes FengSui implements are on by default on a router that was not verified.** On another Huawei HiLink model or a router of another brand, a write was refused until you turned it on, one feature at a time, by typing the model. Now a write FengSui implements for the router works as soon as the router is identified, and you turn off the ones you do not want under Settings → Device. A write FengSui has no implementation of there is refused as before. On a HiLink model the generic writes (LTE band lock, reboot, redial, mobile data, SMS) still need the router to show what each is read back from; on another brand it is what that brand's driver sends (band lock, cell lock and reboot, and SMS where the brand's SMS interface is on record). Every write is still sent once, read back in the same session and alerted on when the read-back differs; the console still asks before each write, and MCP write tools still need `confirm: true`, the agents' switch and a token that may change the router.
- **A lock that cuts the internet is undone after 3 minutes, whoever made it.** On a router that was not verified, the 3-minute fallback used to cover only a band lock made by an AI agent. It now covers every band lock and cell lock, from the console, a token, an agent or Telegram: after a band lock FengSui writes back the bands it read right before it, and after a cell lock it takes the lock off. It does not depend on `LOCK_ROLLBACK_AFTER_MIN`, and it carries on from the lock's own time after the daemon restarts.
- **A write you turned off answers `409 DEVICE_WRITE_DISABLED`**; a write FengSui cannot do on the router still answers `409 DEVICE_UNVERIFIED_READ_ONLY`. Neither opens a session. `schedulerStatus.device.writes` is `experimental` (it was `read_only`) on a model that was not verified, and each feature under `device.features` is `enabled` or `disabled` where it was `consented` or `available`.
- **What is off is kept per model** (`disabledWrites` in the encrypted `settings.json`): a router of another model starts with its own writes on, and the first one is as you left it when it is back. `POST /api/console/experimental` takes `{ feature, enabled }` with no model, and answers with `disabled` in place of `consents`.
- **`set_experimental_write` turns a write off or back on.** The MCP tool keeps its name; `enabled: false` turns one of the default-on writes off, `true` restores it, and it no longer takes the router's model. It answers with the state of every write feature.
- **The one-click AI agent test no longer turns writes on.** They are on already, so starting the test only sets the agents' switches and the token's permissions, and ending it puts those back. It leaves a write you turned off alone.
- **The console says "Unverified model"** where it said "read-only", shows each write's switch on, and no longer asks you to type the model. The note that a write was never checked on a real router stays at each switch and in each write's confirmation.
- **An agent can unlock what it locked.** On MCP, `unlock_rf_locks` is listed wherever the band lock or the cell lock is open; with the band lock off and the cell lock on it used to be hidden, although the lock tool was offered.
- **A feature someone verified counts on a router of any brand.** `VERIFIED_FEATURES` entries name the brand (`family`) and the model as the router reports it; the gate now reads them for ZTE, Pinsu, Tozed, FiberHome, NRadio and OpenWrt routers too, not only Huawei HiLink models. Such a write shows "verified" under Settings → Device, stays in the controls drawer (it used to drop out of it once verified) and its confirmation no longer says it was never checked on a real router.
- **Supported devices lists every model, with four marks.** The page has a row for each of the 250 or so models the interface notes record (Huawei and the HiLink makers, ZTE on both of its interfaces, Pinsu, Tozed, FiberHome, NRadio, OpenWrt modules and routers, UNISOC and Qualcomm reference designs, and D-Link and TP-Link, which FengSui has no implementation for yet), grouped by brand with the usual address and sign-in at the top of each. The marks are now ✓ verified, ? implemented and waiting for a report, △ partly or with a condition (written under the brand's table) and — not available; a cell FengSui does nothing for yet stays empty. What differs between models (developer options on some ZTE models, 5G cells only on zWRT, Fibocom's network modes) is a fact in `src/device-catalog.ts`, and the page is written from it.
- **The device report lists every feature with its result.** `checks` names each feature as `VERIFIED_FEATURES` does, read or write, with `works`, `failed` or `untested` and what that rests on (a read's state, the latest write's read-back), and `access.family` gives the brand; a maintainer can register a report from it without guessing. The issue form says so and accepts routers of brands FengSui cannot choose yet.
- **Settings → Device shows your router's row of Supported devices**: a mark per console module, what its △ cells hang on, and a link to the brand's section on the documentation site. A model the table lacks shows the brand's defaults and a link to report it. The daemon works the row out (`support` on `GET /api/device/profile`); the table itself stays on the documentation site, so the console grows by about 1 KB.
- **A model whose every feature reports confirmed counts as verified.** Once each feature FengSui implements on a model (on its brand) is registered from a report issue, or reported missing on the router, its verification is `report-verified`: Settings → Device and the controls drawer call it verified, the header drops "Unverified model", `MODEL_UNVERIFIED` is not raised, and Supported devices names it with the verified models and gives its row nothing more to report. It is still written the way its brand is, never with the H168-383's requests.
- **The device report says what it found before you read it.** Above a report you create under Settings → Device, the features are listed by what works, what does not, and what is not tried yet, ready for the issue form's two fields.

### Tests
- **The cellular settings are tested on mock routers of every brand**, at the driver (what is sent, how it is read back, what is refused before anything is sent), through the daemon (the gate, the PIN rule, the fallback across a restart, and that no PIN, access point or USSD text is left in a record), over REST and MCP, and in the browser on the ZTE and OpenWrt scenes. The live demo's routes are compared with the real daemon on the same mock routers, answers and write records alike.
- **Browser tests on routers of other brands**: a ZTE mobile router (the battery, the sensors, the SIM card's rows, the ICCID masked, an uptime of "—", a phone's width), an NRadio router (the antenna in the controls drawer, its confirmation and the code written) and an OpenWrt router (a device from a DHCP lease shown as "Link not reported"). The demo's ZTE world is checked against the daemon on the same router (`test/demo-backend-zte.test.ts`). The static demo's size limit goes from 200 to 210 KiB.
- **A failure the test runner leaves out still fails the gate.** On Node.js 26, and on 22 for the end of a group, the runner can leave a result out of its report when a test runs right after an async one; a failing test there showed `fail 0` and the run passed. `npm run test:coverage` and `npm run test:ui` now check the report against what each test sent when it finished: a failure missing from the report fails the run, a passed result missing from it is listed, and a folder that runs fewer tests than its floor in `scripts/test-count-reporter.ts` fails.
- `CONTRIBUTING.md` says how a device report is registered (which results count, what to change, when it shows), and "Other models and brands" explains the report's `checks` and when a cell turns into ✓. The implementation sources (`docs/dev/sources.md`) record the model list, where each model came from and what this step decided (§18.2).

### Upgrading
- **If your router is not an H168-383, check Settings → Device after upgrading.** The writes FengSui implements for your router are now available without being turned on first, including ones you never turned on: on another Huawei model the LTE band lock, reboot, redial, mobile data and SMS (each only where the router shows it can take it), on another brand band lock, cell lock and reboot, and on ZTE, OpenWrt, Tozed and FiberHome routers SMS as well (new in this version, with reading SMS). Turn off the ones you do not want; that holds for the model, and nobody (AI agents and FengSui itself included) can make that write afterwards. Nothing writes on its own: FengSui still writes only when you or an agent you allowed ask for it, and agents still need their own switch and a token that may change the router.
- A script or agent that read `device.writes === "read_only"`, the `consented` / `available` states or `consents` needs the new names above; `DEVICE_UNVERIFIED_READ_ONLY` keeps its meaning for a write FengSui cannot do there.
- **On a ZTE, NRadio or OpenWrt router, more is on by default after upgrading:** redial and mobile data on ZTE, NRadio and QModem OpenWrt routers, the antenna on NRadio routers, and the connected-devices card on ZTE goform, NRadio and OpenWrt routers. Self-healing's automatic redial now works on ZTE, NRadio and QModem OpenWrt routers too (self-healing stays off unless you turned it on). Turn off what you do not want under Settings → Device.
- **On a mobile router, a low battery now raises an alert** (`BATTERY_LOW`, at 20 % while not charging), and on any router a SIM card waiting for its PIN or PUK raises `SIM_LOCKED`; both are on by default. Set `ALERT_BATTERY_LOW_PERCENT=0` to turn the first off. On a router of another brand that reports no uptime of its own, Uptime now shows "—" rather than the connection's duration.
- **If your router is not an H168-383, the cellular settings FengSui implements for it are available after upgrading**, in the controls drawer, through the API and, with `MCP_ALLOW_MUTATIONS` on and the `control` permission, to AI agents. Turn off any you do not want under Settings → Device. A change of the network mode, operator, SIM slot or access point that leaves the router offline for 3 minutes is put back by FengSui; the three `SETTING_*` alerts above are on by default.
- Nothing to change in `.env` or `docker-compose.yml`. On an H168-383 nothing changes: the requests FengSui sends it are the same.

Live events carry no SMS to a token without `sms-read`, and MCP lists only the tools and resources a token may use (still within the agents' switches). Settings → Tokens & AI ticks them when a token is created and edits them later (`POST /api/console/tokens/permissions`, console session only, audited as `token.permissions`; the token's open event stream is closed so it reconnects with its new permissions). `POST /api/console/tokens` takes `permissions`, and still accepts `scope`.
- **Behaviour settings in the console** (`GET` / `POST /api/console/behaviour`, console session only, audited as `settings.behaviour`): the agents' switches and SMS limits (`MCP_ALLOW_MUTATIONS`, `MCP_ALLOW_ACCESS_CONTROL`, `MCP_ALLOW_EXPERIMENTAL`, `MCP_SMS_ACCESS`, `MCP_SMS_SEND_POLICY`, `MCP_SMS_SEND_LIMIT_PER_HOUR`), `REDACT_SENSITIVE_IN_API`, self-healing (`LOCK_ROLLBACK_AFTER_MIN`, `WAN_AUTO_RECONNECT_AFTER_MIN`), alerts (`ALERTS_ENABLED`, `ALERT_NOTIFY_MIN_SEVERITY`, `ALERT_RSRP_THRESHOLD_DBM`, `ALERT_SINR_THRESHOLD_DB`) and SMS behaviour (`SMS_AUTO_MARK_READ`, `DEFAULT_COUNTRY_CODE`). A change applies at once, without a restart: self-healing takes a new window for the lock it watches (turning the rollback on picks up a lock still inside the window; turning it off ends the watch without a write), and the alerts, the notification threshold, the agents' tools and the SMS service follow. Settings has a new General tab (self-healing, alerts, SMS), and the Tokens tab became Tokens & AI with the agents' switches.

The answer says whether FengSui already uses each endpoint and gives its state (supported, unsupported `100002`, restricted `100003`, unknown) and the structure of its answer, tag paths and value shapes, never a value.   - `set_experimental_write` (a model FengSui was not verified on): turns one experimental write on or off with the console's own rules, the router's model typed back to turn one on; it also needs `MCP_ALLOW_MUTATIONS`, the token's `control` permission and `confirm: true`, and is audited as `settings.experimental`.

Restores and permanent deletes are audited (`sms.restore`, `sms.purge`, counts only), `sms:updated` gains the actions `restored` and `purged` (with `expired: true` for the automatic ones), `SmsStatusSnapshot` gains `mirror.trashTotal` and `trashDays`, and `POST /api/sms/delete`, MCP `delete_sms` and the Telegram delete button say how long the message is kept.

## [1.7.5] — 2026-11-09

### Highlights
- **Data files stored without encryption are no longer trusted.** With an encryption key set, a data file in plain JSON is now moved aside and reported instead of read, so a file planted in the data directory cannot bring a console password of its own. Run `doctor` before you upgrade; the upgrade notes say what to do if it reports such a file.
- **Each SMS is sent once.** Pressing Cmd/Ctrl+Enter again while the console was still sending a message sent it a second time.
- **Duplicate-daemon protection works with the recommended setup.** With `PEER_DISCOVERY_ENABLED=true`, the daemon refused to start when the router password was kept in the console rather than in `.env`; the beacon now uses the password saved in the console.

### Security
- **Data files stored without encryption are no longer read.** FengSui read a data file that was plain JSON as it was, the way in from before encryption was required, so anyone able to write the data directory without knowing the key could plant one, such as console settings with a password of their own. Such a file is now moved aside at startup and reported like one that cannot be decrypted. `cpe-dash doctor` names it, and `cpe-dash rekey --plaintext`, run with the daemon stopped, encrypts it when it is yours (or brings back one already moved aside) without keeping an unencrypted copy; a key change never adopts one.
- **Wrong current passwords count across an IPv6 /64.** Changing the console password counts wrong current passwords with sign-in failures, but per address, while sign-in counts per IPv6 /64 (the block a device's privacy addresses rotate in), so a signed-in browser on IPv6 started afresh with each new address. Both now share the /64 count, and the refusal carries the `Retry-After` header the API promises.

### Fixed
- **Indian mobile numbers that begin with 91.** A 10-digit Indian mobile typed without `+` whose first digits are 91 (the 91xx blocks of the 9xxx range) was taken for a number typed with the country code but without `+`, so two digits were lost and the message would have gone to a wrong number; a sender that arrives in national format was filed under that wrong number too. Such a number now reads as a national number, as Italian, Polish and Kazakh numbers already did.
- **Duplicate-daemon protection works with the router password kept in the console.** With `PEER_DISCOVERY_ENABLED=true`, the LAN beacon took its key from `CPE_PASSWORD` in `.env`, which the recommended setup leaves empty because the console keeps the router password, so the daemon refused to start. The beacon now uses the router password saved in Settings → Router, as the router client does; it sends and accepts nothing until a router connection is saved, and follows a newly saved password.
- **The alert for an unsigned router key keeps its remedy.** When a router that signed its encryption key sends one unsigned, FengSui ends the session and the router-unreachable alert gives the reason, cut at 160 characters, which dropped the part naming `CPE_REQUIRE_ECC_SIGNATURE`. The message is now short enough to keep it.
- **An SMS goes out once, however often Cmd+Enter is pressed.** In the reply box and the new-message window, pressing Cmd/Ctrl+Enter again (or holding it down) while a message was going out, or typing meanwhile, sent the same message again, because the browser's form submission ignores the disabled Send button. Each composer now sends one message at a time.
- **A malformed body on a code sign-in answers `BAD_PAYLOAD`.** Choosing the console password with a setup or reset code answered a body that was not JSON, too large or not `application/json` with `VALIDATION_ERROR`, which the API keeps for values its rules refuse.
- **An agent's SMS refused before the router keeps its hourly allowance.** `send_sms` gives back the hourly slot of every attempt that never reached the router, but not when the write gate refused it (another model without consent to send) or no router connection was saved yet, so an agent could be held off for an hour after the owner consented.
- **An agent's incomplete access-control call is refused before the router.** `manage_internet_time_rule` without a rule ID or the rule's days and times, and `set_wifi_mac_filter` with nothing to change, went into a router session before being refused, the latter writing the current list back unchanged; both are now refused at once, as the REST API does.
- **Agents are told every tool that needs `confirm: true`.** The MCP server's instructions named only `reboot_cpe`, though `reconnect_cellular` asks for it too.
- **Queued Telegram notifications are not lost at the edges.** When a new notification pushed the oldest out of a full queue (50, kept while Telegram is unreachable) just as that oldest one was being sent, the next one in line was dropped unsent; and a linked group that became a supergroup lost what was queued for it. Both are delivered now.
- **A quoted `.env` value may have a comment after it.** `CPE_PASSWORD='my pass' # router` was read with its quotes and the comment, so a router password quoted as the configuration page says was imported wrong on the first start (one wrong-password attempt, then the breaker stops). The comment is now dropped and the quotes removed.
- **Contacts match numbers exactly when it matters.** Saving or importing a contact, and the agents' known-recipient rule, matched a number by its last nine digits, so a number in another country ending the same way was merged into an existing contact (renaming it) or counted as known. They now need the same number; naming the sender of a message still forgives the format.
- **Access control recognises your device however its IPv6 address is written.** Blocking, whitelists and time rules never cut off the device that sends the request, but over IPv6 that device was found only when the router and the request wrote its address the same way (zero padding, upper or lower case); it is now matched by the address itself.
- **`restore` and `rekey` flush what they write.** They wrote each store to a temporary file and renamed it into place without flushing it to disk first, unlike the daemon's own saves; on some file systems a power cut right after could leave a short file.
- **A token or code just shown leaves the page when Settings closes.** Closing the settings window hid a newly created token, a Telegram pairing code or a typed router password but kept them in the page until it was opened again; they are now removed when it closes.
- **The code chip works from the keyboard and keeps its label.** Enter or Space on a verification code in the conversation list opened that conversation instead of copying the code, and two quick copies left the chip's label stuck on "Copied".
- **Console settings and the audit log are reported when they cannot be decrypted at startup.** A store that cannot be decrypted (after a mistyped `DATA_ENCRYPTION_KEY`, say) is moved aside, logged and raised as the critical `DATA_QUARANTINED` alert, but the console settings and the audit log were left out of that report, so settings moved aside looked like a fresh install asking for a setup code.

### Documentation

## [1.7.3] — 2026-11-08

### Highlights

### Security
- **The router's encryption key must stay signed.** At login the router hands over the key FengSui encrypts sensitive requests with, signed with a value only the router and FengSui can compute. FengSui already rejected a wrong signature but accepted a missing one. Once a router has signed its key, a login whose key arrives unsigned (an answer altered on the way) is now ended and logged out instead of trusted; this is remembered across restarts and starts over when the router connection changes. Routers that never sign are not affected. `CPE_REQUIRE_ECC_SIGNATURE=false` turns it off.
- **An expiring token's event stream ends when the token does.** `/api/events` closed a stream when its token was revoked, but a stream opened with a token that has an expiry kept running after it expired; it now ends at the expiry, as a console session's stream does.
- **Wrong current passwords count against the sign-in limit.** Changing the console password asks for the current one; wrong answers there were not counted, so a signed-in browser could keep guessing (and keep the password hashing busy). They now count with sign-in failures from the same address, and the change answers `429` once the limit is reached.
- **Agents see more of the rules.** An MCP tool's schema check took inherited names such as `toString` for declared parameters, so they passed where any other unknown parameter is refused; the access-control write tools now carry the same untrusted-data notice about device names as the read tool; and `delete_sms` / `mark_sms_read` state in their schemas how many messages one call may take (20 / 50), which the daemon already enforced.
- **No router request after logout begins, and no retry while yielding.** A request still in flight when its router session logs out (only work that does not wait for its own request leaves one) could be resent with the old session cookie after a closed keep-alive socket; logout now aborts it first. A session that respects the person signed in to the router's page also never tries an occupied admin slot again, whatever retry count it is given (no caller asked for one, so nothing changes today).
- **The router's login signature is compared in constant time.** FengSui checks the signature with which the router proves it knows the password; that check now runs in constant time like FengSui's other secret comparisons, and a router that fails it is refused without opening the wrong-password breaker (now tested).
- **`doctor` finds stores written without encryption, and `rekey` encrypts them.** FengSui still reads a plain JSON store (written before encryption was required), so someone who could write the data directory without knowing the key could plant one. `cpe-dash doctor` now reports such a file, and `cpe-dash rekey` (with the current key as the old one) encrypts it in place, keeping the plain copy beside it. A later release will refuse plain stores; run `doctor` once before upgrading to it.
- **No dialable phone numbers in the guide.** The SMS page showed one number written two ways with a dialable Irish mobile number; it now uses the UK's reserved drama range. `npm run audit:secrets` also refuses a full international number in the working tree unless it comes from the reserved test ranges in `AGENTS.md` (it names the file and line, never the number).

### Fixed
- **Local numbers in Italy, Poland, Russia, Kazakhstan and Hungary.** A number typed without `+` is completed in the default country's own format. Italian mobiles that begin with 39 and Polish numbers that begin with 48 keep those digits (they were taken for a country code typed without `+`, giving a wrong number), and the trunk prefix 8 (Russia, Kazakhstan, in front of the 10-digit number) and 06 (Hungary) is removed as a leading 0 is elsewhere. Senders that arrive in national format follow the same rules. Now that the default country follows the SIM, people in these countries meet this by default.
- **Telegram's send wizard follows the SIM's country too.** A `/new` wizard opened before the daemon had read the SIM refused local numbers until a country was tapped, even after the country became known; it now takes the country once it is known (and still never guesses before).
- **The wizard's country buttons show yours.** Telegram's send wizard offered five fixed countries (Ireland, China, the UK, the US, Hong Kong), so a German SIM's +49 was on none of them and none was marked; the country numbers are read in now comes first, marked.
- **A Kazakh SIM sets the default country.** Its mobile country code (401) was missing, so a number without `+` was refused until a country was chosen; it now means +7, as the dial table's "Russia / Kazakhstan" entry does.
- **Two daemons started at the same moment cannot both run.** The data-directory lock took an empty lock file for a stale one, but a lock is empty for the instant between another process creating it and writing its process ID, so two daemons starting together could both take it and both talk to the router. An empty lock created moments ago now counts as taken.
- **`restore` and `rekey` never leave a store missing.** They moved the old file aside before writing the new one, so a crash or a failed write in between left the store missing and the daemon would start as a fresh install (the old file was kept under another name). The old file is now copied aside and the new one written over it in one step.
- **Stopping during a connection test logs out of the router.** Testing a router connection in Settings logs in on a client of its own; stopping FengSui (or the container) during that test did not cancel it, so the process could exit still logged in and the router's single admin slot stayed taken until the router timed it out. Stopping now cancels and logs out of the test's session as it does for every other.
- **One failing listener no longer hides an event from the rest.** The daemon's internal events (alerts, applied controls, yielding to the router's page) went to each listener in turn, and one that threw stopped the rest from hearing it. The live event stream listens first, so a failure there could have kept an alert or a new SMS from Telegram, or a lock or a reading from the self-healing watch; every listener now hears every event, for the router's readings and SMS as well.
- **A one-time code survives the sign-in limit.** After a few mistyped setup or reset codes, typing the right one was refused for the lockout window and used up at the same time, so a new code had to be issued; the lockout is now checked before a code is spent, as it already was for passwords.

A term anchor written directly under a line of text also becomes an anchor instead of showing as text.

## [1.6.3] — 2026-11-08

### Added
- **A save that fails is said out loud.** Every encrypted store saves in the background, and a failure (a full or read-only data volume, a container running as another user) used to be ignored: the console accepted a new password, token, consent or Telegram link that was gone after the next restart. Such a failure now writes one log line and raises the critical `STORAGE_WRITE_FAILED` alert (pushed like the others) naming the file and the error code, once an hour per file and cause; nothing changes while saves work.

- **Settings → Telegram lists every chat that reaches the bot and unlinks one at a time.** Each chat shows whether it is private or a group, how `/auth` linked it (the token's name, a pairing code, or a group pairing code with the topic it posts to and the only member who may act there) and when; the chats `TELEGRAM_CHAT_IDS` authorizes are listed too, to be removed in `.env`. A chat nobody recognizes can now be unlinked on its own instead of with "Unlink all". New routes `GET /api/console/telegram/chats` and `POST /api/console/telegram/unlink` (console session only, audited with the chat ID's last three digits); privacy mode shows only those digits, and the static demo has the same list.

- **`/metrics` also reports the daemon itself**, to watch it run for weeks on the NAS: resident memory (`process_resident_memory_bytes`), the JavaScript heap, CPU time, the event loop's delay over the last full minute (`nodejs_eventloop_lag_p99_seconds` / `_max_seconds`), open `/api/events` streams and Telegram notifications waiting for Telegram. The names are the usual Node.js ones, so ready-made dashboards and alerts apply; nothing about the router or any device is added.

### Security
- **The saved router password goes only to the saved router address.** A connection test or save that named another address without a password used the saved one, so anyone at an open console could point it at a host of their own on the LAN and receive the router's admin password (a legacy login sends it nearly in the clear) or a SCRAM proof to crack offline, although the console never shows that password. Trying another address now needs its password typed (`400 VALIDATION_ERROR` otherwise, and nothing is sent); the saved address keeps working without retyping, however it is written. Settings → Router stops offering "leave empty to keep the saved password" once the address is changed; the static demo follows the same rule.
- **`cpe-dash reset-login` codes go to the daemon's own host only, also behind a reverse proxy.** `POST /api/setup/reset-code` judged "from loopback" by the TCP peer, so with an HTTPS proxy on the same host every client it forwarded counted as local and only the data-key proof stood in the way. It now uses the client address resolved through `TRUSTED_PROXIES`, so a forwarded LAN client is refused (`401`) while `reset-login` on the host keeps working.
- **A full-access token sent to a Telegram group can no longer link a chat.** A private pairing code shown to a group was already spent there, but a token was only refused: any member who read it could send `/auth` with it to the bot in a private chat and get SMS, codes and the router's controls until its owner revoked it. The token is now marked when it reaches a group (`telegramExposedAtIso` in `GET /api/console/tokens`), links no chat from then on, and Settings → Tokens flags it to be revoked; it keeps working as a token, since revoking it would also cut off whatever else uses it.
- **Revoking a token also unlinks the Telegram chats it linked.** A chat linked with `/auth <token>` stayed linked after the token was revoked, so a leaked token that someone had already used kept them the SMS, codes and router controls through Telegram until "Unlink all". FengSui now remembers which full-access token linked each chat (`telegram.json`, encrypted) and unlinks those chats when that token is revoked; chats linked with a pairing code and `TELEGRAM_CHAT_IDS` stay, and the audit entry says how many chats went. Chats linked with a token before this version are not tied to it: use "Unlink all" once if a token may have leaked.
- **A chat unlinked while Telegram was unreachable gets nothing that was queued for it.** Notifications that could not go out (the WAN down, a `429` window) wait in a queue of up to 50 for 24 hours and were delivered to every chat they were queued for, so a chat the owner had just unlinked, or one linked with a token revoked meanwhile, still received the new SMS and their codes once Telegram answered again. Each queued notification is now sent only if its chat is still authorized at that moment; chats `TELEGRAM_CHAT_IDS` lists are unaffected.

### Fixed
- An access-control change that can cut a device off (block, a whitelist, a time rule) now also refuses when the router marks the machine running FengSui without a MAC address it can use: the host was "identified" but nothing was protected. The H168-383 always reports one; nothing changes there.
- **The console tidies up after a session ends.** When the console falls back to the sign-in page (the session expired or was ended elsewhere), every open dialog closes, so a freshly created token, a pairing code or a typed router password no longer stays on screen over the sign-in page.
- Settings → Telegram creates one pairing code at a time and Settings → Security saves one switch at a time (their controls wait while a request runs); the experimental-write consent never accepts an empty model name; the controls drawer shows the "someone is on the router's page" / breaker / standby notice on other models too; a security switch whose write may have applied (the read-back failed) keeps its position and the drawer reads the router's settings again instead of flipping back; the token name, DMZ address and DMZ switch have accessible names, and the SMS search box's name follows the language.
- **Self-heal's redial budget survives a restart.** The cap of 4 WAN redials in 24 hours and the 10 / 30 / 60-minute backoff were counted in memory, so a daemon restarted during an outage (a deploy, or a crash loop slower than `WAN_AUTO_RECONNECT_AFTER_MIN`) started over with a full budget and the short wait. Both are now saved in the encrypted `state.json` when they change (a redial, the WAN coming back) and taken back at start as far as they fit the current clock; the one-minute retries after a refusal cause no write.
- In a group with topics listed in `TELEGRAM_CHAT_IDS`, the bot answers a command, a reply to one of its cards or a button in the topic it came from, every step of a guided send included; all of it went to General. A group linked with a group code keeps posting to the topic it was linked from, and notifications to such a pre-authorized group still go to General.
- Telegram notifications wait out a `429` (`retry_after`), whether a notification or the bot's own polling got it: queued ones are not retried, and new ones are queued instead of sent, until Telegram's window has passed; sending sooner only lengthened the limit.
- The bot forgets a chat's failed `/auth` attempts once their 10-minute window has passed. It kept an entry for every chat that had ever sent `/auth`, so strangers messaging the bot grew the daemon's memory for as long as it ran; now it holds at most the chats inside the window, which the global limit of 20 failures caps.
- `cpe-dash restore` refuses a backup that a newer FengSui wrote (a store format this version does not read), before it touches anything. It used to put such files in place, after which the daemon refused to start until they were moved back by hand.
- The startup notice about the router password now says only what is true. With the recommended setup (only `DATA_ENCRYPTION_KEY` in `.env`, both passwords chosen in the console) every start claimed that the router's admin password was also the web login and every client's token, and advised setting `API_TOKEN` in `.env`, which has changed nothing since the console took over tokens. It now checks the console store: it names a token that still equals the router password (`API_TOKEN (.env)` after an import without `API_TOKEN`) and says so if the console password is the router password, pointing at Settings → Tokens and Settings → Password; `cpe-dash doctor` no longer repeats the old claim.
- **Lock rollback survives a restart at any point.** The rollback watched a lock in memory, and a restarted daemon re-armed it only while the lock was younger than `LOCK_ROLLBACK_AFTER_MIN`: one restarted after the deadline with the WAN still down (it was away across it, or the rollback was still waiting for someone on the router's page) never rolled the lock back, while one restarted inside the window watched again a lock the WAN had already proved, so a later unrelated outage could clear a working lock. The watch is now kept in the encrypted `state.json` (which lock, and whether the watch has ended): a restart carries an open watch on to the rollback, or to giving up an hour after the deadline, and leaves an ended one alone.
- **A lock rollback no longer undoes a lock applied just before it.** The rollback checked that the lock it was meant for was still in place when it decided, not when its turn in the router queue came: a lock the owner applied in between (typically right at the deadline, to replace the lock that cut the WAN) ran first and was then cleared by the rollback moments later, and the rollback ended that new lock's watch too. The rollback now names its lock and checks it again inside its session, after the queue: a replaced lock is left alone, and only the watch of the lock it was meant for ends.
- Self-heal paces its retries. A redial that failed after it may have reached the router counted against the day's 4 but was tried again a minute later, so a router answering errors used up the day's budget in about four minutes; it now waits its 10 / 30 / 60-minute step like a redial that went through. A lock rollback that found the WAN back inside its session tried again at the next poll that read the WAN down, a router session every 5 seconds while the link flapped; it now looks again after a minute.
- Error messages point at the console, where the router password and the tokens have lived since v1.5.0. The `423 CIRCUIT_BREAKER_OPEN` message (REST and MCP, which agents relay to the owner) said to fix `CPE_PASSWORD` in `.env` and call `reset-breaker`, and refusing that reset said the same; editing `.env` changes nothing now, so both name Settings → Router, where a working password is tested, saved and clears the breaker. The MCP read-only refusal and the `/mcp` `401` no longer speak of `API_TOKEN_READONLY` / `API_TOKEN` but of tokens made in Settings → Tokens, and the contract's recovery note says the same.
- Every dialog's invisible click-outside layer is named in the console's language and no longer takes a Tab stop: keyboard and screen-reader users met an extra English "close" control in all ten dialogs, next to the real close button.

The method is settled before any password goes out: the `password_type` the session's `state-login` check already reads, then the SCRAM challenge, which carries no password; only a challenge refused with `100002` / `100003`, redirected (how some models answer an endpoint they lack) or answered without one leads to the legacy login, and a missing or unknown `password_type` sends no password at all. Each session submits the password once, with one method, and the breaker, the yielding to a person on the router's page and the final logout apply to every method alike. A router that has logged in with SCRAM (in a background session, now or before a restart, or in the connection test a save used; a test that is not saved never changes what the daemon remembers) never gets a legacy password, not even from the console's connection test; the read-only probe scripts (`npm run probe:*`), being H168-383 tools, keep to SCRAM from their first session. So the H168-383's requests stay exactly as they were (`test/h168-wire.test.ts`). If such a router refuses the SCRAM challenge, the session fails without sending the password and the daemon shows the router as unreachable, which raises `CPE_UNREACHABLE` with the reason. For a router replaced by an older model at the same address, deploy a fresh container (a new, empty `data` directory), or set the new `CPE_ALLOW_LEGACY_LOGIN_AFTER_SCRAM=true` (default `false`) until the new router is tested and saved: it lets only the console's test look for a legacy login, and the daemon reminds you at start while it is on. Legacy logins never use the encrypted channel. `docs/dev/protocol.md` appendix A.8–A.9.
- **A connection test names how it logged in**: besides model and firmware, Settings → Router shows the login method (SCRAM, SHA-256 or Base64), where the tokens came from (`webserver/token` or `SesTokInfo`) and whether the encrypted channel is on (`loginScheme`, `tokenFlow`, `ecc` in `ConnectionTestResult`). New failure reasons: `password_change_required` (`115002`; change the password on the router's page first), `unsupported_login` (no known `password_type` and the SCRAM challenge refused; the password was not sent), `scram_refused` (a router that logged in with SCRAM before refused it; the password was not sent) and `unconfirmed_login` (an answer to a legacy password FengSui cannot place). Settings → Device adds the token source, the breaker banner explains a `115002` latch and opens Settings → Router, and the static demo reports the same fields.
- **The daemon identifies the router it talks to** (for other Huawei models; it changes nothing on the H168-383, whose login, polling and writes stay exactly as they were, while another model's identification makes it read-only, see above). Once after the daemon starts and whenever the console tests or saves a connection, one read session sends ten fixed GETs (`docs/dev/protocol.md` appendix A.7), giving each at most 5 s so a router that leaves an unknown endpoint hanging cannot hold the admin slot long, and records the model, firmware and WebUI version, the login (`password_type`, SCRAM, ECC, token source), the LTE bands from `net-mode-list` and, per endpoint, supported / unsupported (`100002`) / restricted (`100003`, which is not unsupported) / unknown (another code, no answer, or an answer too big or cut off: one odd endpoint never fails a connection test that logged in). It never runs in the 5 s poll, yields to a person on the router's page and never logs in past an open breaker. If the start finds someone on the router's page, an open breaker or no answer, the identification waits without sending anything and runs right after the first read that gets in, ahead of the reads still queued (it gives up after three failed attempts in a row, until the next start or connection test). `GET /api/device/profile` serves it to any signed-in caller with the verification status: verified, a new build of a verified model (still only a warning, ADR-007), or an unverified model; like the device report below, it takes a second pass for anything that looks like an identifier. The client also counts the router's error codes per endpoint.
- **Settings → Device** in the console shows the identified model, firmware, WebUI version, login, encryption, verification state, features and the endpoint probe, and creates the device report (download JSON or copy) with a reminder that it holds no identifier and that sharing it is your choice. The static demo shows the demo router the same way.
- **A desensitized device report** (`GET /api/console/device-report`, console session only; tokens get `403 CONSOLE_ONLY`), for owners of other models to attach to a compatibility issue if they choose. It holds structure, not values: for each probed endpoint its state, error code, tag paths and value shapes (`int`, `hex(18)`, `text(12)`…), the router error codes counted since start, and what FengSui does with the router (writes allowed or locked, and per read section whether the model provides it). Values appear only for an allowlist (model, firmware and WebUI version, `password_type`, small switch numbers, LTE band numbers), and a second pass through `src/sanitize.ts` replaces anything that still looks like a MAC, an IP address, an IMEI / IMSI / ICCID or a phone number. Nothing is uploaded.
- **Notes on other Huawei models** (`docs/dev/protocol.md`, appendix A), the groundwork for supporting more than the H168-383: identification and capability endpoints, the token and login flows, error codes and the models the reference project lists, each with its source and marked unverified. Login-free reads on the H168-383 showed that `device/basic_information` (model only) and `user/state-login` answer before login, while the firmware and WebUI versions need a session. The facts come from [Salamek/huawei-lte-api](https://github.com/Salamek/huawei-lte-api), now thanked in both READMEs; FengSui contains none of its code and does not depend on it.
- **The logo has a single source**, `web/brand/logo.svg`. The build turns it into the console's icon and ships it as the favicon; tests keep all three in step. `npm run brand:trace -- concept.png` turns a flat logo concept (a light / dark side-by-side is fine) into that file, tracing the outlines to within 0.6 px. `docs/dev/brand.md` describes the contract and how to change the logo next time.

### Changed
- `MODEL_UNVERIFIED`, `SELF_HEAL_READ_ONLY` and the `409 DEVICE_UNVERIFIED_READ_ONLY` message now say that writes on another model are locked by default and point to Settings → Device for experimental writes, instead of saying every write is locked.
- The telemetry snapshot reports the model and marketing name the router gives, or an empty string: it used to fill in `H168-383` and `HUAWEI 5G CPE Ultra 6` when the router named none.
- The breaker also latches on `115002` (the router wants its admin password changed on its own web page) instead of trying again every poll, and on any answer to a legacy `user/login` password other than `OK` and the codes that refuse a login before the password is checked: an unknown code, but also a page, an empty, cut-off or oversized body, or a redirect, which FengSui never follows and which used to look like a lost request (breaker code `unconfirmed`). On a model nobody verified such an answer may have counted as a wrong attempt; until now a body without an error code had the password sent again every five seconds. On a router identified as an unverified model the SCRAM proof follows the same rule (an unknown code, an answer without a server signature, a redirect); the H168-383 and a router not identified yet keep the verified handling, where such an answer fails the session and the next one tries again. Its structure scan also treats a `>` inside a quoted attribute and CDATA sections as XML does, so neither can garble an allowlisted value such as the model. An allowlisted model, version or marketing name is now kept only when all of it is letters, digits, spaces and `._()+-` within 64 characters, and dropped whole otherwise: it used to have other characters replaced with `?` and was cut at 64, which could leave a fragment of an identifier too short for the second pass to recognize.
- A stored identification is checked when `state.json` is read; one this version cannot read (written by another version, say) counts as not identified yet instead of breaking `GET /api/device/profile`, and the start-up identification runs as usual.
- `get_cpe_session_status` with `probeLive` reports `passwordType: null` when the router names none (it used to say `"4"`).
- A wrong console password on the sign-in page just says so; it no longer adds that after an upgrade the password is still the `API_TOKEN` from `.env`, which misled anyone who chose the password with the setup code ("Forgot password?" is right there).
- **New logo: 月白 · 回声** (a high arc and its lower echo). It replaces the beacon seal in the header, on the sign-in page and as the favicon. In the console both arcs take the theme's colours: the main arc is the primary hue muted toward the ink, the echo leans toward the page, so every theme and custom accent gets a matching two-tone mark. The favicon follows the system's light or dark setting.
- The console's size limits are relaxed for the features still to come: the first-paint target is now 80 KiB gzip (it was 60 KiB; the build reports it and does not fail on it), and the build fails when first paint and the parts loaded on demand together pass 160 KiB (it was 120 KiB, which the console had reached). The static demo's limit stays at 200 KiB. `npm run check` now builds the console as well (well under a second), so a console over its limit fails the local gate just as it fails CI, a release and the Docker build; until now the gate passed while the build that ships failed.

The line stays as a comment for other Linux hosts; `mem_limit` still applies. A deployment that added `pids_limit` to its own compose file by hand can delete it.

The daemon keeps the last 100 alerts, and the console forgot on every page load when its alerts panel was last opened, so any warning or critical among them came back as new (a hard refresh always showed the same one). ## [1.4.0] — 2026-11-02

### Added
- **A guide to connect an AI agent, in the console.** The robot icon in the header ("AI agents" at the bottom of the dashboard on phones) shows the MCP endpoint for the address in use and builds, from a token you paste (`API_TOKEN_READONLY` recommended), a prompt to hand to Claude Code, Codex or another coding agent (it sets the server up, checks it, and keeps router writes behind your explicit request), the `claude mcp add` command and the `mcpServers` JSON. The token stays in the page, masked on screen; the shell command quotes it so no character in it can run as shell syntax. Over plain HTTP the copy buttons fall back to a selection copy.
- **Sponsor links**: a heart in the console header and footer opens GitHub Sponsors, and the repository has a `FUNDING.yml` (GitHub Sponsors, Buy Me a Coffee), as in cpe-sms.
- **A warning when the router runs a firmware build FengSui was not verified on.** Huawei updates the H168-383 on its own, and the private API that locks, access control and SMS rely on may change with it. When the router reports a model or firmware build (service pack included) outside `VERIFIED_FIRMWARE` (`H168-383 4.4.0.1(H1006SP19C00)`), a `FIRMWARE_UNVERIFIED` warning is raised once per build and remembered across restarts; writes are not blocked. On Telegram it is followed by a ready-made prompt to hand to Claude Code in the repository: it names the build, keeps the agent read-only on the real router (no writes, no `.env`, no login retries, probes run by you one at a time) and ends with adding the build to the list once it checks out.
- **Optional WAN self-healing, off by default** (both write to the router without anyone asking). `LOCK_ROLLBACK_AFTER_MIN` clears every band and cell lock once when the WAN is still down that many minutes after a lock (it must come back and stay up for 2 minutes to keep the lock), so a lock to a band without coverage no longer leaves the house offline until someone on the LAN undoes it. `WAN_AUTO_RECONNECT_AFTER_MIN` redials a WAN down that long, then after 10, 30 and 60 minutes, at most 4 times in 24 hours, and never reboots. Both act on fresh telemetry only, queue like any control (yielding to a human on the WebUI, no login while the breaker is open), re-read the WAN state and the mobile-data switch in the same session before writing, and raise `LOCK_ROLLED_BACK` / `LOCK_ROLLBACK_FAILED` / `WAN_AUTO_RECONNECT` / `WAN_RECONNECT_EXHAUSTED`.
- **Read-only Bearer token `API_TOKEN_READONLY`** (optional, off by default). It reads every REST route and SSE and may trigger read sessions (refresh, scan, SMS preview and sync); on `/mcp` it sees and may call only read-only tools. Any write (controls, SMS send / read / delete, contacts, `reset-breaker`) answers `403 READ_ONLY_TOKEN`. Give it to dashboards, scripts and AI agents that should never change the router; it must differ from `API_TOKEN` and `CPE_PASSWORD`. The stdio bridge uses whatever `API_TOKEN` its own `.env` holds, so a read-only agent gets the read-only value there.

### Security
- **`npm run audit:secrets` closes two gaps.** Tracked Wireshark `.pcapng` (and compressed `.pcap.*`) captures, Fiddler `.saz` sessions and `.vcf` contact exports now fail the gate like `.har` and `.pcap`, and explicit `any` is caught as a type argument (`Record<string, any>`), in tuples, return types and unions, not only after a colon. The rules are exported and covered by `test/audit-gate.test.ts`.
- **CI and release workflows pin every GitHub Action to a full commit SHA** (the version stays in a comment for Dependabot), so a moved tag in an action's repository cannot change what runs in the job that pushes images. Releases now run one at a time. `test/ci-config.test.ts` keeps both in place.
- **Startup warns when `API_TOKEN` falls back to the router password.** Unset, the router's admin password is also the web login, the Bearer token in every REST and MCP client config and the secret sent to Telegram with `/auth`. Startup now says so next to the existing `DATA_ENCRYPTION_KEY` notice.
- **Telegram `/auth` works only in a private chat with the bot.** Sent in a group, it linked the whole group, so every member could read SMS and one-time codes, send and delete messages and see alerts, and the token message could stay visible where the bot may not delete messages. Groups are refused with a warning to delete the token; a group can still be pre-authorized with `TELEGRAM_CHAT_IDS`.
- **The duplicate-daemon beacon no longer hands the LAN a fast oracle for the router password.** Every 15 s each daemon broadcast a beacon signed with a key that was one HKDF of `CPE_PASSWORD`, so any device on the LAN could test password guesses offline at billions per second, out of reach of the router's 3-attempt lockout. The key is now derived with memory-hard scrypt (beacon v2). A weak router password is still guessable, only far slower: use a strong one, or set `PEER_DISCOVERY_ENABLED=false` when only one daemon ever runs. Upgrade every host at once: v1 and v2 daemons do not see each other.
- **Access control fails closed.** If the router's host list could not be parsed, came back empty or did not mark the machine running FengSui (`IsLocalDevice`), every protected device silently dropped out of the check, so a block, whitelist, list edit or time rule could cut off the daemon's host. Such changes are now refused with `400` before anything is written; changes that only let devices back on (unblock, filter off, deleting a time rule) still work.
- **MCP agents can no longer widen the SMS recipient policy themselves.** With `MCP_SMS_ACCESS=full` and `MCP_SMS_SEND_POLICY=known`, a prompt-injected agent could file any number with `upsert_contact` and then `send_sms` to it. Contacts an agent creates are now stored as `source: "mcp"` and do not count as known for MCP sends until you save the number yourself (web console, Telegram or a vCard import); an agent renaming one of your contacts leaves it yours.

### Fixed
- **Telegram notifications raised while the WAN is down are no longer lost.** The NAS reaches Telegram through the router's own cellular link, so `WAN_DOWN`, the alerts raised during an outage and SMS that arrived meanwhile all failed to send and were only logged. Notifications that fail on a network error (or a `429` / `5xx`) are now kept in memory (up to 50, for 24 hours) and delivered in their original order as soon as Telegram answers again; new ones queue behind them, and a delayed SMS card still routes replies to its sender. Errors Telegram means for good (a blocked bot) are not retried.
- **The Telegram poller honours `429 retry_after`.** It retried after its own 1.5 s backoff, which only prolongs Telegram's rate limit; it now waits at least as long as Telegram asks (capped at an hour) and stays interruptible by shutdown.
- **Data that cannot be decrypted at startup is reported.** A store whose file no longer decrypts (typically `CPE_PASSWORD` changed while `DATA_ENCRYPTION_KEY` was unset) moved the file aside and started empty without a word, so contacts or Telegram links seemed to vanish. The daemon now logs each such file with the way back and raises a critical `DATA_QUARANTINED` alert.
- **Long Telegram replies are delivered.** Replies over Telegram's length limit were cut at a fixed character count, which could land inside a tag or an entity; Telegram then rejected the whole message, so `/chat` on a thread of long messages answered nothing. Cuts now stop before a tag or entity and close the tags left open.
- **A band lock that names one RAT keeps the other RAT's lock in the record.** The router keeps what a command does not write (the LTE mask goes through net-mode, NR bands and cell locks through lock-freq), but the recorded lock state reset the omitted RAT: locking NR after an LTE lock reported LTE unlocked and raised a false `LOCK_DRIFT` alert, locking LTE after an NR lock forgot the NR lock, and an LTE-only band lock hid a cell lock that was still in force. The omitted part is now carried over.
- **Every write in the controls drawer asks first.** UPnP, DMZ, the firewall switches, MLO / DBHO and the antenna buttons wrote on a single tap, although the drawer promised confirmation. Each now shows what the change does first, in amber when it weakens protection or can drop the connection (firewall or a filter off, UPnP or DMZ on, the firewall MAC list on, the external antenna with nothing plugged in). Enabling DMZ with an empty address is refused like an invalid one.
- **Access-control pickers respect privacy masking**: a device without a name is shown by its masked MAC, not the full one. List separators and the overnight marker now come from the dictionaries, so English no longer shows Chinese punctuation.
- **A stop during startup is clean.** The SIGTERM / SIGINT handlers were installed only after startup finished, and a stop that did arrive (for example `docker stop` right after `docker start`) let startup carry on: polling began and the HTTP port was bound after shutdown. Handlers are now installed first, and startup checks for a stop after each wait, so nothing starts after it.
- **Importing a large vCard no longer freezes the daemon.** The contact index was rebuilt after every card, so a 5000-card export took seconds of blocked event loop (SSE, REST and an open router session all stalled; about 5 s on a desktop CPU, longer on a NAS). Cards are now indexed as they are added, with one rebuild at the end: the same import takes tens of milliseconds.
- **An old Telegram confirmation card can no longer send a newer draft.** Every "Send now" button carried the same callback data, so tapping it on an earlier card sent whatever draft was current. Each card's button is now bound to its own draft; a stale one answers that the flow expired.
- **MCP `manage_internet_time_rule` can update and delete rules again.** Its `id` was capped at 16 characters, but the H168-383 names rules by TR-069 path (`InternetGatewayDevice.X_FireWall.TimeRule.1.`), so every update or delete through MCP failed with `VALIDATION_ERROR`. The limit is now 128.

### Upgrading
- Upgrade every host that runs a FengSui daemon at the same time: the duplicate-daemon beacon moved to v2, and v1 and v2 daemons do not see each other.
- Group chats linked earlier with `/auth` stay linked. To unlink them, rotate `API_TOKEN` (every `/auth` link is revoked); keep a group on purpose by listing its ID in `TELEGRAM_CHAT_IDS`.
- If startup now prints the `API_TOKEN` notice, set a dedicated random `API_TOKEN` and update your MCP clients and Telegram link with it.
- Lock rollback and WAN redial stay off until `LOCK_ROLLBACK_AFTER_MIN` / `WAN_AUTO_RECONNECT_AFTER_MIN` are set. `.env` is bind-mounted as a single file, so recreate the container after editing it (`docker compose up -d --force-recreate`); a plain restart keeps the old file.
- A router on another firmware build than `4.4.0.1(H1006SP19C00)` raises `FIRMWARE_UNVERIFIED` once after the upgrade. `data/` needs no migration: the state file only gains the firmware notice.
- For AI agents, set `API_TOKEN_READONLY` and hand that token out (the console's agent guide uses it); keep `API_TOKEN` for yourself.

## [1.0.1] — 2026-10-31

### Fixed
- **The reveal buttons now reveal.** `REDACT_SENSITIVE_IN_API` (on by default) masked snapshots when they were captured, so the web console never received the real IMEI, IMSI, own number, WAN addresses, MAC or cell fingerprints and its eye buttons changed nothing. The daemon now keeps the plain values (still encrypted at rest) and applies the switch per caller: the logged-in web console always receives the real values and masks them on screen until revealed; Bearer REST and SSE clients and MCP tools and resources receive redacted copies.
- **No more look-alike values.** Redaction no longer substitutes plausible placeholders (a private WAN address rewritten into `192.168.8.x`, DNS shown as `198.51.100.42`, LAN clients renamed `lan-client-NN` with documentation MACs and `fe80::1`). Every redacted value now reads as a mask: a kept prefix plus `*`, or `<REDACTED>`. LAN IPv4 addresses stay readable.

### Changed
- `POST /api/session/reset-breaker` applies a changed `REDACT_SENSITIVE_IN_API` to REST, SSE and MCP without a restart.
- Telemetry and topology a v1.0.0 daemon cached already masked are discarded on the first start after the upgrade; the next poll (seconds) replaces them.
- The web console's "Redacted by server" badge is gone, since the console no longer receives redacted data.

### Upgrading
- No `.env` change is needed. If you set `REDACT_SENSITIVE_IN_API=false` only to make the reveal buttons work, you can set it back to `true`: it now affects Bearer API and MCP clients only.

## [1.0.0] — 2026-10-31

First production release: one container that monitors a Huawei 5G CPE Ultra 6 (H168-383, firmware 4.4.0.1), serves the web console and runs the SMS gateway through a single router admin session.

### Web console
- Dashboard: carrier-aggregation capsule, per-carrier RF readings (RSRP / RSRQ / SINR rings, MCS, MIMO, transmit power), health, daily and monthly traffic rings with thresholds, live and historical throughput / signal charts with brush zoom, neighbor cells with "Lock to this cell", LAN / 2.4G / 5G client topology with lease countdowns.
- Messages: threads, search, long SMS, one-tap OTP copy, compose with GSM-7 / UCS-2 segment count, read / delete with confirmation, contacts with vCard import; an accepted send whose status poll timed out shows as "Submitted · unconfirmed", never as failed.
- Controls drawer: LTE / NR band lock, unlock, security switches, cellular reconnect and reboot with confirmation.
- Distinct states for polite yielding (`409`), the anti-lockout breaker (`423`), daemon restarts (`503`) and expired sessions; privacy masking of IMEI, IMSI, phone numbers, WAN addresses and SMS content.
- Four themes (Paper, Dawn, Polar Night, Violet Abyss), six accents, Chinese / English; no CDN, strict CSP, 59.8 KiB gzip first paint.

### Daemon
- `MutexSessionScheduler` as the only path to the router: ephemeral sessions (~26–260 ms) with a guaranteed logout, two-layer yielding to a human admin, a persistent `108006` / `108007` circuit breaker, a duplicate-daemon guard and graceful `SIGTERM` shutdown.
- Telemetry, neighbor scans, topology and settings with a two-tier time-series ring (5 s for 3 h, 60 s for 7 days); alert engine with sustain windows and hysteresis.
- SMS mirror, contacts and Telegram state encrypted at rest (AES-256-GCM); Telegram two-way bot; HMAC-signed webhooks.
- REST, SSE and a zero-dependency MCP server on `/mcp` (13 core tools, up to 10 SMS tools) plus the stateless `cpe-dash mcp` stdio bridge.

### Container and CI
- Multi-stage `Dockerfile` (`node:26-alpine`, non-root, no `node_modules`, `HEALTHCHECK`), hardened `docker-compose.yml` for Synology DS923+, CI on Node 22.x and 26.x with a container smoke test, and a tag-triggered release of `linux/amd64` + `linux/arm64` images to GHCR.

### Fixed in this release
- A session waiting only on its hold deadline no longer lets the event loop exit early (found by the first CI run on Node 22).
- Web console: a `2xx` response with a stalled or truncated body is an error instead of `null`; history-chart gradients, brush listeners and duplicate renders no longer accumulate in a tab left open for weeks.
